# Release Management Framework Prototype

A browser-based release workspace for agreeing a controlled release process across Development, Test, QA, Pre-Production, and Production. It captures release identity, entry/exit checks, evidence references, named approvals, communication drafts, and proposed IBM/KAD responsibilities. The existing GitHub Actions build embeds its environment, commit, package name, and workflow run URL in the main site's deployed package. When hosted from that package, the board can link the currently served Dev or Prod build to its originating Actions run.

The app evaluates configured criteria and records a simulated sequential gate. **It does not build, transfer, or deploy code; read live workflow status; verify service health; send communications; authenticate users; or create an audit-grade approval record.** The embedded manifest identifies the build currently serving the page and links to its Actions run; it is not a live GitHub status integration. Gate state is stored in the current browser's local storage. Do not use it as an operational production approval system.

## Run locally

From the repository root:

```bash
python3 -m http.server 5173 --directory src
```

Open <http://localhost:5173/releasemanagement/>. Edits are local to that browser. Use **Reset example** to restore the proposed starter criteria.

When opened locally, the board reports that no deployment manifest is available. The manifest is generated by the GitHub Actions build for the deployed site; it is deliberately not committed to the source tree.

## Current capability and proposed target model

The repository currently has real Development and Production deployment configuration. A feature branch is reviewed by PR checks; merging to `main` starts the application release workflow. That workflow builds and deploys Development, then separately builds and deploys Production. The package for each environment carries a manifest identifying its environment, package, source commit/ref, and parent Actions run. Since a successfully served page reads its own package manifest, the board can show which current Dev or Prod package is serving it and link to the run that produced it.

This is a one-way identity link, not a live workflow status API: it cannot show in-progress/failed jobs, compare all environments from one page, or verify application health. Dev and Prod are still separate builds rather than promotion of one immutable artifact. Test, QA, and Pre-Production have no deployment targets in this repository. See [the current release flow](../../docs/release-flow.md). Those additional stages below are a proposed operating model, not existing infrastructure.

| Stage | Purpose and team guidance | Suggested exit evidence | Deployment status in this repo |
|---|---|---|---|
| Development | Engineering integration, feature work, unit tests, and developer smoke testing. Keep changes traceable to reviewed source; use non-production data. | Build and unit-test results, smoke-test result, known-defect list, source commit/artifact identity. | Current Development target. |
| Test | Technical, integration, and system validation by delivery/test teams. Verify interfaces, configuration, and technical behavior. Do not treat a technical pass as business acceptance. | Test run and result, defect summary and dispositions, environment/configuration notes. | Proposed; no distinct target is configured. |
| QA | Independent regression and agreed business acceptance. Test against approved scenarios. Fixes return through the controlled development/test route; avoid feature changes during sign-off. | Signed QA/regression results, business acceptance, open-defect/exception list. | Proposed; no distinct target is configured. |
| Pre-Production | Production-like rehearsal and operational readiness. Validate deployment and rollback procedures, monitoring, access, support coverage, and change record. | Rehearsal and rollback results, approved change/runbook, support rota, monitoring checks. | Proposed; no distinct target is configured. |
| Production | Authorized production change, health verification, business/service acceptance, and handover. Use the approved artifact and window; do not substitute or rebuild it after approval. | Deployment result and artifact identity, health checks, release communication, handover and follow-up record. | Current Production target; environment approval can be configured in GitHub. |

These criteria are starting recommendations only. The client must confirm test thresholds, severity definitions, evidence systems, data rules, approvers, exceptions, maintenance windows, and rollback authority before using them operationally.

## Proposed promotion contract

1. Assign a release owner and record a source commit plus immutable artifact/package identity.
2. Build and run development checks. Record the results and developer smoke test before requesting Test.
3. Promote the same identified candidate forward only after its current-stage entry criteria, exit criteria, evidence, and named approval are complete. Do not rebuild between environments. If a change is needed, create a new candidate and repeat the affected checks.
4. In Test, the delivery/test team owns technical and integration evidence. A passing Test gate is not QA or business acceptance.
5. In QA, QA and the named business representative own regression/acceptance sign-off. Record deviations and obtain an explicit exception decision; do not silently waive a gate.
6. In Pre-Production, rehearse the planned change and rollback, verify monitoring/runbooks and support coverage, then obtain the designated change approval for the production window.
7. In Production, deploy the approved artifact through an authorized deployment mechanism, run health checks, notify stakeholders, and record accept/rollback and handover outcomes.

The prototype checks gates in order and records each decision locally. “Record gate” only advances the simulated workflow; it is not a code promotion or GitHub Environment approval. The current repository pipeline creates separate Development and Production packages, so an immutable single-artifact promotion model would require a future pipeline change and explicit client agreement.

## Communication guidance

The project team should receive a release notice at candidate creation, a readiness/defect summary before QA acceptance, a go/no-go and window notice before Production, and an outcome/handover update after deployment. Each message should include release/version, source/artifact identity, target stage, status, evidence/change-record links, decision owner, next action and time, known risks, and support contact. Production notices should include the approved window and rollback/escalation route.

Use the Communications view to edit a per-stage audience, subject, and draft. It never sends a message. Confirm distribution lists, communication channels, timing/SLA, and who is authorized to issue notices with the client.

## IBM and KAD: items to confirm

The prototype deliberately leaves named owners blank. Validate the RACI and contractual service boundaries with the client rather than treating these suggestions as assigned commitments.

| Party | Proposed areas to clarify |
|---|---|
| IBM | Product/platform support boundary; deployment and environment constraints; technical escalation and incident route; platform monitoring/access requirements; support hours and release-window availability; evidence or runbook inputs IBM can provide. |
| KAD | Client business owner and acceptance authority; environment/access readiness; business test scenarios and data approval; change/CAB approval and maintenance window; stakeholder distribution lists; operational support and rollback decision authority. |
| Delivery / QA | Build and artifact traceability; automated/manual test results; defect triage; implementation and rollback plans; release coordination and complete evidence package. |

Names, approval thresholds, support response times, out-of-hours coverage, and escalation contacts are all **TBD** pending client and IBM/KAD confirmation.

## Automation roadmap

The current GitHub Actions and Terraform setup targets Development and Production only. A safe implementation sequence is:

1. Agree the stage purposes, criteria, evidence, approver roles, defect thresholds, communications, and exception/rollback rules using this prototype.
2. Decide whether Test, QA, and Pre-Production need separate Azure resources, logical slots, or process-only gates. Confirm access, data, network, monitoring, cost, and ownership requirements.
3. Extend infrastructure and GitHub Environments only for approved real targets. Add environment-scoped permissions and required reviewers; keep Production protected.
4. Change the release pipeline to build one immutable artifact and promote that exact artifact with traceable checks and approvals. Add health verification and a tested rollback path before enabling unattended steps.
5. Integrate GitHub Actions/Azure status, durable audit storage, identity/authorization, and approved email/chat/change-management channels. Keep credentials and privileged actions server-side.

Do not enable live automation until the target environment design, authorization model, approvals, evidence retention, and rollback responsibilities are approved. This standalone folder is included within the repository's `src/` package; no dedicated App Service or deployment workflow is added by this prototype. The current pipeline's manifest is the initial traceability link; a future live status integration needs authenticated server-side GitHub access or an approved webhook receiver and durable shared storage. Never place GitHub credentials in browser code.
